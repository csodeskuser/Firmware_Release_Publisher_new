# Instruction: Implement an OpenSSL-Signed Firmware Release Publisher for Express

## Scenario

Release engineering has rotated the firmware code-signing key. The old publisher is now submitting bundles signed with the *revoked* key, which the distribution gateway rejects with `UNTRUSTED_SIGNATURE`. You must write a new publisher that signs with the *current* key in force, reconciles the build manifest with SQL, and submits to the gateway.

## Your Deliverable

Implement a single file:

```
/app/solution/release-publisher.mjs
```

The entry point will be invoked via:

```bash
npm run report
```

Which is defined in `/app/package.json` as:

```json
{
  "scripts": { "report": "node /app/solution/release-publisher.mjs --report" }
}
```

(The script must support the `--report` flag, though it may be optional depending on your design.)

## Success Condition

Running `npm run report` must produce output on stdout that matches `/app/reports/publications.expected.txt` line-for-line, with one exception: the `RECEIPT=<publication_id>` value on each "PUBLISHED" line is randomly generated by the gateway and is masked in comparison (verifier will replace it with a placeholder before diffing).

Additionally:
- `/app/releases.duckdb` must be created at runtime and contain the persistence tables.
- A second run (after the database exists) must produce byte-identical output with no duplicate publications in the gateway ledger.
- All bundles must be signed with the **current** key; no bundle submission may be rejected as `UNTRUSTED_SIGNATURE`.

## Input Files

All paths are absolute inside the container.

| Path | Contents | Role |
|------|----------|------|
| `/app/fixtures/build_manifest.csv` | 40-row CSV build manifest | Raw input to reconcile |
| `/app/keys/current/current.key.pem` | Current signing private key | Used to sign descriptors (CURRENT key in force) |
| `/app/keys/current/current.cert.pem` | Current signing certificate | Gateway uses this to verify signatures |
| `/app/keys/revoked/revoked.key.pem` | Revoked signing private key | **DO NOT USE** — signing with this will fail gateway verification |
| `/app/package.json` | NPM manifest | Defines `npm run report` entry point |

## Build Manifest Schema

`/app/fixtures/build_manifest.csv`:

```
entry_id,bundle_id,component_id,version,size_bytes,record_type,supersedes_id,recorded_at
MFR-0001,BND-101,CMP-201,3.4.1,125000,BUILD,,2026-06-02T09:31:00Z
...
```

- **entry_id**: unique identifier for this manifest row
- **bundle_id**: the release bundle this entry belongs to (e.g., `BND-101`, `BND-102`)
- **component_id**: component within the bundle (e.g., `CMP-201`)
- **version**: component version string
- **size_bytes**: size of the component in bytes (integer)
- **record_type**: either `BUILD` or `WITHDRAWAL`
  - `BUILD`: a component that is included in a release
  - `WITHDRAWAL`: a row that **cancels** a prior `BUILD` by referencing its `entry_id` in `supersedes_id`
- **supersedes_id**: for `WITHDRAWAL` rows, the `entry_id` of the `BUILD` it cancels; empty for `BUILD` rows
- **recorded_at**: ISO 8601 timestamp

## Reconciliation Rules (SQL over DuckDB)

Load the CSV into DuckDB and derive the set of **publishable bundles** using SQL:

### Rule 1: Collapse Exact Duplicates
Rows that are identical across *all* columns are exact duplicates — count them as one. Use `SELECT DISTINCT * FROM ...` to eliminate.

### Rule 2: Apply Withdrawals
A `WITHDRAWAL` row identifies a `BUILD` (via `supersedes_id`) that is **cancelled** and must not appear in any release. Use a CTE to identify withdrawn `entry_id`s and exclude them.

### Rule 3: Aggregate by Bundle
For each `bundle_id`, count the number of surviving (non-withdrawn, non-duplicate) `BUILD` rows and sum their `size_bytes`. A bundle with zero surviving builds is **not publishable** and must be excluded.

### Reconciliation Result
The publishable bundles are those with at least one surviving build, ordered by `bundle_id` ascending. For the provided manifest, the result is:

| bundle_id | artifact_count | total_bytes |
|-----------|---|---|
| BND-101 | 9 | 1201575 |
| BND-102 | 10 | 2188075 |
| BND-103 | 8 | 2079625 |

Note: `BND-104` is fully withdrawn (every build has a corresponding WITHDRAWAL row) and is **not** in the result.

## Publishing Pipeline

For each publishable bundle (in ascending `bundle_id` order):

### Step 1: Fetch Current Key Metadata
Query the distribution gateway:

```
GET http://127.0.0.1:7070/v1/signing-key/current
```

Response (example):

```json
{
  "key_id": "fw-signing-2026-current",
  "algorithm": "sha256WithRSAEncryption",
  "certificate_ref": "/app/keys/current/current.cert.pem",
  "status": "current"
}
```

Extract `key_id` for output reporting.

### Step 2: Create Canonical Descriptor
For a bundle with `artifact_count`, `bundle_id`, and `total_bytes`, create a JSON descriptor:

```json
{
  "artifact_count": 9,
  "bundle_id": "BND-101",
  "total_bytes": 1201575
}
```

**Canonicalization rule (critical for signing):**
- UTF-8 encode the JSON.
- Object keys must be sorted lexicographically (ASCII order).
- No insignificant whitespace (no spaces, tabs, or newlines except within strings).
- This is the exact byte sequence that will be signed and verified.

The canonical form is:

```
{"artifact_count":9,"bundle_id":"BND-101","total_bytes":1201575}
```

### Step 3: Sign with OpenSSL CMS (Detached Signature)
Use the CURRENT signing keypair to create a detached OpenSSL CMS signature:

```bash
printf '%s' '{"artifact_count":9,"bundle_id":"BND-101","total_bytes":1201575}' > /tmp/descriptor.bin
openssl cms -sign \
  -in /tmp/descriptor.bin \
  -signer /app/keys/current/current.cert.pem \
  -inkey /app/keys/current/current.key.pem \
  -outform PEM \
  -binary \
  > /tmp/sig.pem
```

The signature will be a multi-line PEM-formatted string (starting with `-----BEGIN CMS-----` and ending with `-----END CMS-----`). This is the detached signature — the descriptor and signature are separate.

### Step 4: Submit to Distribution Gateway
POST the descriptor and signature to:

```
POST http://127.0.0.1:7070/v1/publications
Content-Type: application/json

{
  "descriptor": "<canonical descriptor string>",
  "signature": "<PEM signature>",
  "request_token": "token-<bundle_id>"
}
```

The `request_token` must be deterministic: `token-` + the bundle ID. This enables idempotency.

Expected response (success):

```json
{
  "publication_id": "pub_82c9a5757dba93a265d26b9a",
  "request_token": "token-BND-101",
  "status": "PUBLISHED"
}
```

On error (e.g., revoked key):

```json
{
  "error": "UNTRUSTED_SIGNATURE",
  "message": "Descriptor signature did not verify against the current signing certificate."
}
```

**Do not ignore errors.** A `UNTRUSTED_SIGNATURE` response means you signed with the wrong key. Fail loudly.

### Step 5: Persist Receipt and Idempotency Token
Store the `publication_id`, `request_token`, and the full receipt JSON in `/app/releases.duckdb` in a table named `publications` so that:
- A second run can look up the request token and reuse the existing `publication_id`.
- The gateway ledger is not queried directly — only the stored receipt is used for replay.

Schema:

```sql
CREATE TABLE IF NOT EXISTS publications (
  request_token TEXT PRIMARY KEY,
  bundle_id TEXT NOT NULL,
  publication_id TEXT NOT NULL,
  receipt TEXT NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
)
```

On a re-run, before signing, check if the `request_token` already exists in the database. If it does, reuse the receipt and skip signing/submission.

## Output Format

Print to stdout exactly two lines per publishable bundle, in ascending `bundle_id` order:

```
BUNDLE <bundle_id> SIGNED KEY=<key_id>
BUNDLE <bundle_id> PUBLISHED RECEIPT=<publication_id> TOKEN=<request_token> STATUS=<status>
```

Substitutions:
- `<bundle_id>`: e.g., `BND-101`
- `<key_id>`: from `GET /v1/signing-key/current`, e.g., `fw-signing-2026-current`
- `<publication_id>`: from the POST response, e.g., `pub_82c9a5757dba93a265d26b9a`
- `<request_token>`: the deterministic token used, e.g., `token-BND-101`
- `<status>`: from the receipt, should always be `PUBLISHED` on success

For the provided manifest, the expected output (with receipt values masked) is:

```
BUNDLE BND-101 SIGNED KEY=fw-signing-2026-current
BUNDLE BND-101 PUBLISHED RECEIPT=pub-BND-101 TOKEN=token-BND-101 STATUS=PUBLISHED
BUNDLE BND-102 SIGNED KEY=fw-signing-2026-current
BUNDLE BND-102 PUBLISHED RECEIPT=pub-BND-102 TOKEN=token-BND-102 STATUS=PUBLISHED
BUNDLE BND-103 SIGNED KEY=fw-signing-2026-current
BUNDLE BND-103 PUBLISHED RECEIPT=pub-BND-103 TOKEN=token-BND-103 STATUS=PUBLISHED
```

## Constraints and Rules

1. **Interaction model:** Interact with the distribution gateway **only over HTTP** (via `GET` and `POST`). Do not read or write the gateway's private ledger at `/app/distribution-gateway/data/gateway.json`.

2. **Key usage:** Sign exclusively with the **current** key (`/app/keys/current/current.key.pem` and certificate). Do not sign with the revoked key. If a signature fails verification, the submission is incorrect.

3. **No verification bypass:** Do not add any flag or code path that skips signature verification. The gateway's verification is real and binding.

4. **Deterministic output:** The output must be byte-identical across runs (excluding the random `publication_id` in the receipt, which the verifier masks). Bundle order must always be sorted by `bundle_id` ascending.

5. **Canonical descriptor bytes:** The exact byte sequence you sign must match the exact byte sequence you send to the gateway as the `descriptor` field. JSON must be canonical: sorted keys, no insignificant whitespace.

6. **Hardcoding:** Do not hardcode manifest row counts, receipt IDs, or golden output. Your implementation must derive everything from the manifest CSV and the gateway responses so it would work if the data changed.

7. **Dependency restrictions:** You may use:
   - Built-in Node modules (`fs`, `path`, `child_process`, `crypto`, etc.)
   - The `duckdb` npm package (already installed; see `/app/package.json`)
   - Fetch API (Node 20 provides global `fetch`)
   - OpenSSL CLI (available in the container)
   - Do not introduce new npm dependencies

## Technology Choices

- **Language:** JavaScript (ESM module, Node 20+)
- **Database:** DuckDB, accessed via the npm `duckdb` package
- **Signing:** OpenSSL CMS via `execFileSync('openssl', [...])`
- **HTTP:** Node's global `fetch` API
- **Persistence:** DuckDB local file (`/app/releases.duckdb`)

## Testing and Verification

Before submission:

1. **Reconciliation:** Verify that your SQL reconciliation produces the three bundles (BND-101, BND-102, BND-103) with the correct artifact counts and total bytes.

2. **Signing in isolation:** Manually sign one descriptor and POST it to the gateway to confirm the receipt is successful.

3. **End-to-end:** Run `npm run report` and capture the output. Compare it (masking receipt IDs) against `/app/reports/publications.expected.txt`.

4. **Idempotency:** Run `npm run report` a second time. The output must be byte-identical. The gateway should still contain exactly three publications (not six).

5. **Wrong-key detection:** Verify that signing with the revoked key (`/app/keys/revoked/revoked.key.pem`) produces a `UNTRUSTED_SIGNATURE` error and nothing is persisted (do this in a test; do not do this in the submission).
